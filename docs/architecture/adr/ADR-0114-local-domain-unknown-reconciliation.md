## Accepted narrow decision

An Engineering-only exact-Root operation may establish one of these facts, without re-dispatching the original tool or rewriting its ingress, settlement, claim, or original business result:

1. **Committed:** the original claim is `succeeded`, its exact `result_json` identifies the original Artifact, and the durable original-key Artifact agrees with the same owner, Workspace, conversation, Task, AgentRun, Root, action, request/input hashes, content hash, and idempotency key. Current local `byq_strategy_validate` does not create an `artifact_submission_receipts` row, so that original-key row must be absent; a submission receipt from another operation is not proof of this validation. The Artifact and succeeded claim must be attributable to the same atomic transaction; an Artifact found only by name or a successful receipt for another Root is insufficient.
2. **Uncommitted:** the exact old dispatch and any Backend callback have irrevocably ended; after acquiring the existing authority, Root, request/ingress, session, claim, and task locks in their established order and waiting for competing transactions to finish, the original claim is still `executing`, has no committed result, and the exact original-key Artifact/submission receipt is absent. The atomic success path means it cannot have committed its Artifact without also changing the claim to `succeeded`. Artifact absence alone, a signed runner cleanup alone, an expired HTTP timeout, or an Adapter restart is insufficient. A lock timeout, unknown callback liveness, or any late-write path is **HOLD**.

The first implementation covers **exactly one** `byq_strategy_validate` claim and its one matching unknown tool ingress; it may not cover a second unknown row by implication. The already observed native identity, original request ID, exact sequence/event/arguments/settlement hashes, domain observation/evidence, claim ID, and exact request/input/idempotency hashes must match. Validate the full owner/Workspace/public conversation/private session/trace, authority boot/epoch, runtime generation, Root, AgentRun, native registration, Task, and complete ingress and claim snapshot. Any other pending or unknown ingress, domain claim, sibling Root, changed key/input, missing or orphaned row, new dispatch, or uncertain effect is **HOLD**. No caller-supplied label can classify an arbitrary business operation as local validation. StrategyVersion creation remains out of scope.

### Proposed contract

1. Extend the existing recovery request with the separately observed durable
   Gateway trace tail. Keep `initial_sequence`, its binding lower bound, and
   the existing N→I→J exact-retry rules; the maximum is not evidence of the
   actual durable trace tail.
2. A new boundary may be allocated only after proving that the durable trace
   tail and the existing binding sequence are aligned. An actual, newly accepted
   recovery transition then produces a framework-neutral `session.reattached`
   event at the next new sequence before a subsequent prompt is admitted.
   A one-position gap does not prove that its position was never allocated.
   It states only that the public conversation can attach
   to a verified execution context; it never claims restoration of the original
   Agent, completion of a task, or settlement of a business unknown.
3. Keep the existing binding `sequence`, settlement receipt, previous boot,
   authority and signed Root scope unchanged. Persist the boundary separately
   in a strict `recovery_boundary` record in that binding, including its exact
   canonical event bytes and digest, next sequence, current boot/authority
   epoch, and pending/acknowledged state. Update it through the existing binding

   never be overloaded with it. Reuse the same boundary bytes on exact retries;
   do not create a different timestamp/body for an allocated sequence. This
   uses the existing binding and recovery response, not a new journal,
   collector, endpoint, scheduler or Agent harness.
4. If an existing binding is already ahead of the durable trace, HOLD unless
   original event bytes can be appended unchanged. Newly created and durably
   stored boundary bytes from step 3 can satisfy this exact-replay condition;
   the size of a gap cannot. No historical sequence is reclaimed for a new event.
   Gateway validates the existing owner/Workspace/session/trace/boot/Root and
   terminal/cleanup proofs, then appends the supplied genuine boundary through
   the normal TraceStore contract, then acknowledge the exact event digest via
   the existing recovery request before allowing the next turn. Runtime marks
   only that persisted boundary acknowledged; this does not update the old
   binding sequence or allocate another sequence. An already durable identical
   event is idempotent; conflicting bytes, unverifiable provenance or any
   uncovered gap HOLD. Append confirmation must precede prompt admission. A
   larger `initial_sequence` alone never authorizes filling a gap.
5. Preserve TraceStore's consecutive-sequence requirement, ordinary lifecycle
   projection, business approvals, unknown fences and cancellation semantics.
   Do not lower a persisted sequence or fabricate historical ready/terminal
   events. Account for each actual I/J transition explicitly; do not create
   repeated boundary events merely to advance a counter.
