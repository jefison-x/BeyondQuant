# Stock Pool Contract — Phase 34

This contract operationalizes ADR-0020. Keywords **MUST**, **MUST NOT**,
**SHOULD**, and **MAY** are normative.

## Domain records

### Pool identity

A pool identity MUST expose:

- `pool_id`, `owner_principal`, `name`, optional `description`;
- immutable `pool_type`: `custom`, `index`, or `dynamic`;
- `status`: `active`, `inactive`, or `deleted`;
- `current_snapshot_id` and `current_version_number`;
- `created_at`, `updated_at`, and lifecycle audit metadata.

`pool_id` MUST be globally generated by Backend. Catalog reads MUST be owner
scoped. Deleted identities MUST be excluded unless an explicit bounded
`include_deleted` operator/domain query is authorized.

### Immutable snapshot

A snapshot MUST expose:

- `snapshot_id`, `pool_id`, `schema_version`, and per-pool `version_number`;
- `membership_fingerprint` and `snapshot_fingerprint`;
- `pool_type`, normalized `definition`, normalized `provenance`;
- optional `effective_at`/`effective_trade_date` according to type;
- `member_count`, `weight_mode`, `weight_sum`, and immutable `created_at`;
- paginated member projection and owner-safe reference summary.

Snapshot identity uses canonical UTF-8 JSON with sorted object keys and no
insignificant whitespace. Decimal weights are canonical strings. Members are
ordered by canonical symbol. Mutable timestamps, actor, pool name,
description, status, and `version_number` MUST NOT enter the hash.

### Members and weights

Each member contains `symbol`, optional `weight`, and bounded type-specific
display metadata. Display name, industry, and live quote data are joins, not
snapshot identity, unless a future Accepted ADR explicitly freezes them.

The Backend MUST reject:

- an empty membership;
- non-canonical, duplicate, or out-of-contract symbols;
- mixed weighted/unweighted members;
- zero, negative, non-finite, over-one, or over-precision weights;
- weighted sums outside `1 ± 0.00000001`;
- weights for non-members; and
- unlabelled percent-to-fraction conversion.

## Write behavior

### Create

User Product API create is limited to `custom`. Backend generates the pool and
first snapshot atomically. Trusted index/dynamic creation uses a separate
service capability and validates the provenance required by ADR-0020.

### Metadata update

Name/description updates require owner scope and optimistic identity version
checking. They MUST NOT create a membership snapshot.

### Snapshot update

Member, weight, definition, or trusted provenance updates require:

- `expected_current_snapshot_id`;
- an `idempotency_key`;
- a complete desired semantic snapshot, not an ambiguous partial JSON merge;
- owner/trusted-writer authorization appropriate to `pool_type`.

Backend canonicalizes and hashes inside one transaction. Identical semantic
content returns the existing snapshot and does not increment the version.
Stale expectation or same idempotency key with different content returns
conflict. No update mutates an existing snapshot.

### Lifecycle

Activation, deactivation, and delete require an idempotency key and bounded
reason. Repeating the same target state is successful and does not duplicate
audit records. Deleted is terminal. A deleted pool cannot accept metadata or
snapshot writes. Snapshot/history/reference reads needed for replay remain
available through owner/domain-authorized routes.

## Provenance

`custom` provenance records `source=custom`, creator/last editor through audit,
and optional normalized filter definition. Filter results are not authoritative
until persisted as snapshot members.

`index` provenance MUST include `source=index`, canonical index symbol,
provider, provider dataset ID, effective trade date, original weight unit,
normalization contract version, and ingestion manifest/reference. Tushare is
the configured provider unless proven provider-independent canonical data has
passed validation. BaoStock and AKShare are forbidden.

`dynamic` provenance MUST include `source=dynamic`, producer ID and version,
rule fingerprint, evaluation time, and immutable input references. Phase 34
MUST NOT invent a generic rules runtime or let Product DSH evaluate it.

## Consumer rules

- New consumers MUST bind `stock_pool_snapshot_id`, validate owner equality,
  and reject inactive/deleted pools.
- Replays MUST resolve the stored snapshot directly and MUST NOT dereference
  the current pool pointer.
- Backtest requested symbols and signals MUST be subsets of the snapshot and
  MUST NOT combine the snapshot with another index-universe selector.
- Research artifacts MUST record snapshot lineage.
- Paper authorization MUST use an account/universe snapshot binding; pool
  edits MUST NOT change an existing binding.
- Index `as_of` selection MUST resolve the latest effective snapshot whose
  effective date is not after the requested date.

## Product API surface

The Phase 34 Product API MUST provide owner-scoped, bounded operations for:

- catalog list and pool create/detail;
- metadata update;
- current member/weight list and complete snapshot update;
- definition/filter and provenance/reference projections;
- snapshot history and historical snapshot detail;
- activation, deactivation, and tombstone delete;
- trusted index constituent/as-of reads.

Exact paths are added to `product-api.openapi.yaml` with implementation. The
browser MUST call `/api/product/...` only and MUST NOT submit authoritative
fingerprints, snapshot IDs, trusted provenance, or provider operations.

## MCP surface

Phase 34 MUST add bounded normalized `byq_pool_*` capabilities for catalog,
detail, snapshot/history inspection, allowed custom-pool writes, and lifecycle
actions. Tool results MUST not expose storage schemas or provider credentials.
DSH MUST not access PostgreSQL or raw Backend endpoints. Mutating tools MUST
preserve trusted owner/actor context, idempotency, and optimistic concurrency.

## Migration contract

Migration of current BYQ `stock_pools` MUST be logical, repeatable, and
transaction-safe:

1. inspect and classify each row;
2. normalize/validate owner, type, symbols, weights, and provenance;
3. create the identity and one immutable snapshot while preserving `pool_id`;
4. record a migration manifest and deterministic counts/checksums;
5. quarantine invalid or ambiguous rows with reason codes;
6. rerun without duplicating identities or snapshots; and
7. verify current pointers and fingerprints after import.

Non-custom type claims without trusted provenance MUST be quarantined or
explicitly downgraded only through a reviewed operator mapping; they MUST NOT
be silently accepted. Community data is not imported by this migration.

## Required acceptance tests

Phase 34 cannot be complete until automated tests prove:

1. owner isolation and non-disclosing unauthorized responses;
2. canonical symbol ordering, deterministic fingerprints, and duplicate
   rejection;
3. exact weight validation, unit handling, and stable decimal serialization;
4. no-op snapshot reuse, monotonic changed versions, idempotency conflict, and
   optimistic-concurrency conflict;
5. rename/lifecycle changes do not create snapshots;
6. inactive/deleted pools reject new references while historical references
   remain resolvable;
7. delete is a tombstone and cannot orphan or erase snapshots;
8. index as-of selection has no look-ahead and provenance is trusted;
9. backtest/research/paper consumers freeze and enforce snapshot membership;
10. migration is idempotent and invalid rows are quarantined;
11. Product API and `byq_pool_*` MCP boundary parity; and
12. all five UI detail projections use persisted real Product API data.

Chrome MCP evidence MUST cover desktop and mobile catalog/detail, custom pool
create/edit, weight validation, snapshot history, lifecycle actions, and at
least one read-only index/as-of flow. The Community feature checklist and the
Phase 34 visual reference evidence MUST be linked from the completion report.
