# BeyondQuant Architecture

This document is the normative architecture boundary for BeyondQuant (BYQ). Rules marked MUST or MUST NOT are architecture constraints. Any exception requires an ADR before implementation.

## A. Overall architecture

BeyondQuant is divided into five logical planes:

1. Product Plane
2. Agent Plane
3. Quant Domain Plane
4. Data Plane
5. Engineering Plane

The intended product path is:

```text
User
  ↓
BYQ Frontend
  ↓
BYQ Gateway
  ↓
DSH + dsh-byq
  ↓
BeyondQuant MCP
  ↓
BYQ Domain
  ↓
Data / Factor / Strategy / Backtest
```

The Engineering Plane is separate from the Product Plane:

```text
Engineering DSH
  ↓
Codex Subagent
  ↓
isolated Git worktree
  ↓
tests
  ↓
Draft PR
```

Product Plane conversations MUST NOT acquire Engineering Plane privileges by ordinary prompt escalation.

## B. DSH responsibilities

DeepSeek Harness (DSH) owns general-purpose agent infrastructure:

- Agent Loop
- Session
- Context
- Compaction
- Skills
- Presets
- Subagents
- Generic Workflow
- Web Search / Fetch
- Tool Registry
- MCP Client
- Generic Guards
- Generic Human Interaction
- Code Runtime infrastructure

BYQ MUST NOT reimplement these generic capabilities when DSH can provide them. A replacement or duplication requires a documented ADR with a concrete necessity and compatibility impact.

## C. BYQ responsibilities

BYQ exclusively owns quantitative and product-domain capabilities, including:

- A-share semantics
- Market data abstraction
- Tushare integration
- Factor definitions
- Factor computation
- Strategy definition
- Strategy validation
- Backtest execution
- ResearchTask
- Experiment
- Artifact
- Business Approval
- RBAC
- Audit
- WorkflowTrace
- Quant Research Methodology
- Domain invariants
- Business idempotency

DSH MUST remain domain-agnostic. Quantitative domain invariants MUST be enforced by BYQ contracts and services, not by generic agent prompts alone.

## D. MCP boundary

The BeyondQuant MCP boundary is the only stable capability boundary between Agent Plane and Quant Domain Plane.

DSH MUST NOT directly access BYQ PostgreSQL.

DSH MUST NOT directly access Redis for BYQ business state.

DSH MUST NOT directly import BYQ backend internals.

Agent-to-domain communication MUST go through BeyondQuant MCP. The MCP surface MUST expose domain capabilities and validation contracts rather than storage internals.

## E. Strategy-code boundary

Strategy code generated by a user-facing agent is a Domain Artifact, not Application Source Code.

The intended strategy flow is:

```text
Agent
  ↓
StrategyDraft Artifact
  ↓
validate_strategy
  ↓
Business Approval if needed
  ↓
Backend
  ↓
Backtest Worker
```

Product Agent MUST NOT directly write `services/backend` source code. A generated strategy MUST NOT be saved as BYQ application source. Strategy artifacts MUST have explicit ownership, validation, provenance, and approval semantics.

## F. Workflow boundary

DSH Workflow is responsible for research orchestration, subagents, tool orchestration, and generic agent execution.

BYQ Domain Workflow is responsible for Artifact state, Approval state, Backtest job state, Experiment lineage, ResearchTask lifecycle, and business idempotency.

These are separate state machines. They MUST NOT be merged into one implicit workflow model. A DSH run may produce BYQ domain events, but it does not own the resulting business state.

## G. Workflow visualization

The frontend MUST NOT directly depend on DSH event schemas.

The required translation path is:

```text
DSH Event
  ↓
BYQ Gateway
  ↓
BYQ WorkflowTrace Contract
  ↓
Frontend
```

WorkflowTrace is a framework-neutral BYQ contract. If DSH is replaced, the frontend MUST NOT need to be reimplemented merely because framework event schemas changed.

WorkflowTrace SHOULD be able to represent:

- Agent nodes
- Subagent nodes
- Tool nodes
- Artifact
- Approval
- Backtest
- Experiment
- Errors
- Repair
- Completion

## H. Browser and web boundary

BYQ SHOULD prefer DSH Web Search / Fetch for general web research. BYQ MUST NOT become a second general-purpose browser-agent framework.

If real-browser capability is later required, it SHOULD be implemented as an independent DSH web-browser plugin. Chrome / Chromium, CDP, and Playwright are acceptable implementation technologies, but the plugin MUST NOT become BYQ Core.

## I. Product source-code protection

This is the highest-security architecture boundary.

Production Product DSH:

- MUST NOT mount the BeyondQuant source repository.
- MUST NOT expose source-editing tools.
- MUST NOT expose Git write tools.
- MUST NOT expose Engineering Codex capability.
- MUST NOT allow a normal conversation to elevate itself into Engineering privilege.

If a normal user asks Product Agent to modify BYQ source code, Product Agent MAY explain, analyze, and generate an EngineeringTask. It MUST NOT directly modify source code.

## J. Engineering Plane

Engineering Plane is an independent security domain. It may:

- Analyze bugs
- Analyze metrics
- Detect regressions
- Propose improvements
- Modify code
- Run tests
- Create Draft PRs

Engineering Plane MAY use isolated Git worktrees, feature branches, DSH coding tools, Codex subagents, tests, lint, integration tests, contract tests, and E2E tests.

Engineering Plane MUST NOT:

- Push directly to `main`
- Force push
- Deploy directly to production
- Perform automatic destructive database migrations
- Merge automatically during the initial operating model

Engineering agents MUST use disposable worktrees, for example `/home/jefison/projects/.byq-worktrees/`, rather than directly modifying `/home/jefison/projects/BeyondQuant`.

## K. Agent versus execution

Agent roles MUST NOT be independently containerized merely because they have different names. Roles such as Chief Quant Researcher, Market Researcher, Fundamental Researcher, Quant Researcher, Strategy Designer, Strategy Optimizer, Backtest Analyst, and Quant Verifier SHOULD be represented as DSH Presets, Skills, or Subagents running in the DSH runtime.

Execution capabilities may be independently containerized:

- backend
- mcp
- backtest-worker
- data-worker
- postgres
- redis
- optional browser worker
- optional engineering agent

## L. Container principle

Future core components MUST be independently deployable, independently upgradeable, and fault isolated.

The target product topology is:

```text
frontend
gateway
dsh
mcp
backend
backtest-worker
data-worker
postgres
redis
```

The Engineering Plane is independent:

```text
engineering-dsh
```

This document defines topology principles only. It does not authorize creating containers in the initialization phase.

## M. DSH dependency policy

DeepSeek Harness is expected to iterate quickly. BYQ MUST:

- Pin an exact DSH version.
- Disable automatic latest-version upgrades.
- Maintain a compatibility adapter where integration requires one.
- Maintain contract tests for the adapter and MCP boundary.
- Run an upgrade test before any production upgrade.

BYQ MUST NOT fork DSH. A fork would require a new architecture decision and explicit governance review.

## N. Quant Learning

BYQ may later establish a Quant Learning Loop:

```text
ResearchTask
  ↓
Experiment
  ↓
evidence
  ↓
validated lesson
  ↓
candidate Quant Skill
  ↓
review
  ↓
BYQ Quant Skill
```

Ordinary chat content MUST NOT directly become trusted quantitative knowledge. Lessons require evidence, validation, review, provenance, and a controlled promotion path.

## O. Engineering Learning

BYQ may later establish an Engineering Learning Loop:

```text
Trace / Metrics / Error
  ↓
Problem hypothesis
  ↓
EngineeringTask
  ↓
isolated code change
  ↓
tests
  ↓
Draft PR
```

Software evolution MUST be verifiable, auditable, and reversible. Engineering learning MUST NOT bypass worktree isolation, tests, review, or branch protection.

## Governance

Changes to DSH boundary, MCP boundary, database boundary, WorkflowTrace, authentication, Engineering Plane, container topology, strategy runtime, data-provider abstraction, or Artifact / Approval semantics require an ADR. See `docs/architecture/adr/README.md`.
